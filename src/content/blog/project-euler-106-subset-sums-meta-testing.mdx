<h3>Project Euler #106 — Subset Sums Meta Testing</h3>
<p>Alright, here we go, the final boss of this subset sums series of problems:<br /><a href="https://www.hackerrank.com/contests/projecteuler/challenges/euler106/problem?isFullScreen=true">https://www.hackerrank.com/contests/projecteuler/challenges/euler106/problem?isFullScreen=true</a></p>
<p>Let’s go over the examples first: Assuming &#123;a,b,c,d&#125; is in ascending order:</p>
<p>&#123;a,b&#125;,&#123;a,c&#125;,&#123;a,d&#125;,&#123;a,bc&#125;,&#123;a,bd&#125;,&#123;a,cd&#125;,&#123;a,bcd&#125;,&#123;b,c&#125;,&#123;b,d&#125;,&#123;b,ac&#125;,&#123;b,ad&#125;,&#123;b,cd&#125;,&#123;b,acd&#125;,&#123;c,d&#125;,&#123;c,ab&#125;,&#123;c,ad&#125;,&#123;c,bd&#125;,&#123;c,abd&#125;,&#123;d,ab&#125;,&#123;d,ac&#125;,&#123;d,bc&#125;,&#123;d,abc&#125;, &#123;ab,cd&#125;,&#123;ac,bd&#125;,&#123;ad,bc&#125;</p>
<p>So, there should be a way to logic out which pairings needs to be checked for equality.</p>
<p>First of all, we can eliminate all unequal subsets. That only leaves the singles and the doubles.</p>
<p>Then, we can eliminate all the singles, since they’re definitely different.</p>
<p>So, it comes down to the three pairs: (&#123;ab&#125;,&#123;cd&#125;), (&#123;ac&#125;,&#123;bd&#125;), and (&#123;ad&#125;,&#123;bc&#125;).</p>
<p>Now, only knowing that the numbers are strictly increasing, we then know that (ab,cd) cannot be equal, since it’s the two smaller numbers against the two larger numbers:</p>
<p>If a &lt; b &lt; c &lt; d, then a &lt; c and b &lt; d, meaning a + b &lt; c + d. We can rule (ab,cd) out.</p>
<p>Then, a &lt; b and c &lt; d, so a + c must be less than b + d. We can rule (ac,bd) out.</p>
<p>Lastly, a &lt; b but d &gt; c! So, a + d ? b + c. The lone ambiguity is (ad,bc).</p>
<p>Boy, this will be a doozy to suss out; it doesn’t seem so far to have a ton in common with the exact ideals of the previous special subset problems, but in terms of optimizing, it should be similar in that you only need to evaluate specific paired terms. It’s a matter of identifying those paired terms.</p>
<p>What it does have in common, though, is efficiently creating these unique set pairs. That’s probably where the evaluation(s) will be; how can I generalize what I just did, and in less than O(n²) time?</p>
<p>—</p>
<p>Since 1000000 choose 2 is explosively high, it’s clear that there’s got to be a way to skip all of the trivial cases and count more directly: no generating lists or sets, just some way of mathing it out.</p>
<p>But this makes sense; say we had set &#123;a,b,c…z&#125;. There’s no need to compare any other two-set against &#123;y,z&#125;, all other 2-sets will be smaller. And any other set will be bigger than &#123;a,b&#125;. And perhaps there are other intuitions about the second rule that might help? Knowing that a + b &gt; z, a + b + c &gt; y + z, etc. So, for a set-pair to be ambiguous, they must “overlap” in terms of where they pull from in the set. &#123;a,z&#125; vs. &#123;b,y&#125; is ambiguous.</p>
<p>But, also considering &#123;a,y&#125; &lt; &#123;b,z&#125;, since both terms on the left are less than a respective term on the right, that’s not ambiguous. Maybe that’s it; <strong>can every element in one set be matched in the same inequality with an element from the other</strong>? Might need to build out two 3-sets to compare…</p>
<p>&#123;a,b,c&#125; &lt; &#123;d,e,f&#125;, &#123;a,b,d&#125; &lt; &#123;c,e,f&#125;, &#123;a,b,f&#125; ? &#123;d,e,c&#125;</p>
<p>At this point it might be worth building out something that can actually build the sets, let alone test them:</p>
<p>I think I’ll need to see the combinations before I can really see any patterns…</p>
<pre>def buildPairSetsBrute(array, setSize):<br />    """<br />    Prints the sorted, same-size subset pairs from an array.<br />    """<br />    combos = list(combinations(array,setSize))<br />    pairs = set()<br />    for i in range(len(combos)):<br />        for j in range(i + 1, len(combos)):<br />            combo1,combo2 = combos[i],combos[j]<br />            if not set(combo1) &amp; set(combo2):<br />                pairs.add((combo1,combo2))<br />    pairs = list(pairs)<br />    pairs.sort()<br />    for pair in enumerate(pairs, 1):<br />        print(pair)</pre>
<p>After my simple implementation, I was able to clearly see the pattern: <strong>A pair needs to be tested if all the elements cannot be evenly paired with each other such that they are always less-than or greater-than.</strong></p>
<p>So, building the sets in ascending order is helpful; they will already be sorted.</p>
<pre>def consistent(setPair):<br />    """<br />    Checks whether every element of the arr1 is pair-wise less than the elements of arr2<br />    """<br />    return all(x &lt; y for x, y in zip(setPair[0], setPair[1]))</pre>
<p>Then, it should be about summing the inconsistent sets directly instead of building all the set-pairs and checking them; there should be some mathematical intuitions about this! For example, &#123;a,z&#125; can be ambiguously paired with &#123;b,c&#125;,&#123;b,d&#125;…&#123;b,y&#125;. But also &#123;c,d&#125;,&#123;c,e&#125;…&#123;c,y&#125;. The combinatorics may come in handy again! Or, at least, some <strong>summation formulas.</strong></p>
<p>The rest of the implementation can be an exercise for the reader; build out some ways to see what you need to see for the patterns!</p>

The polynomial solution may involves several layers of polynomial summing! Get your algebra hats on! I’m coming across binomial expansions, Pascal’s Triangle…</p>
